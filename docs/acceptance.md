The supplied original closed-loop intent is exercised as: load/create starters → discover → move/resource → failed capture → successful named target capture → party/storage → trainer restrictions/switch/medicine → multi-level reward → learning/evolution → second partner item evolution → flee → defeat → recovery → save/restore/reencounter. Nicknames are assigned in creation/opponent content and retained; no rename UI is claimed. This maps the supplied route, not an unseen verbatim Section 5 document.

Each complete-flow rejection checks same state reference, revision and adapter dispatch count. Latest receipt replay checks no extra consumption/admission/reward; conflicts and old receipts reject. Full suites additionally exercise malformed checkpoints, engine-advanced faults, release/abandon failures, capacity/numeric bounds, alias isolation and fixed pending-recovery invariants. These are actual execution results, not proof of every possible game or hostile JS object. All stateful battle assertions use controlled trusted-local adapters, not a production engine, asynchronous platform or anti-cheat authority.

Rules differ materially: XP thresholds [0,5,15,30] vs [0,2,6], HP tables/cap, finite resources vs none, fixed HP2 recovery retaining condition/resources vs full HP/condition/resource recovery. Final HP is [2,2,5] vs [5,8,2], same final species and levels [3,3,1], without core edits.
