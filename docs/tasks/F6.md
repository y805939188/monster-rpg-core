# F6 — controlled in-battle actions and capture

Classification: LARGE (already authorized). Status: parent approved A then B dependency-review sequence; A PASS, B PASS; full F6 independent review PASS. One parent feature; internal substeps do not change the parent's scope or limits. F5 source/contract gate PASS. Full F6 must pass before F7.

## Why two dependent review points

F5 currently has synchronous setup/release and one accepted durable snapshot. F6 introduces engine advancement before core validation. Fault handling, terminal release failure, replay and resource/stock/ownership effects therefore share a new commit boundary. Reviewing that boundary before adding medicine/flee/capture reduces the chance of duplicate debit, partial capture admission or misreported rollback. No acceptance is removed.

## F6-A — command/checkpoint/recovery foundation

Approved first implementation slice: extend existing synchronous session with one in-flight monotonic command, runtime session/generation and revision correlation, validated actor/target identity, complete permanent-field checkpoints, and move/switch operations sufficient to exercise the boundary. Preserve F5 setup/release-only adapters: add an optional action capability; unsupported action rejects before engine execution, not by breaking begin/release.

Store only the latest accepted confirmation/receipt and current fault. Exact latest accepted replay returns already_applied; same-ID conflicting payload, older consumed ID, future ID or wrong correlation rejects. Validate complete reported identities/species/HP/persistent conditions/move definitions/resources and party membership before any durable commit. Switch only to eligible owned party member; preserve its current HP/resources rather than reconstructing it.

An adapter throw or invalid confirmation after invocation faults the session; no automatic engine retry, no further actions. Explicit abandonFaultedEncounter releases the local handle and retains the most recent committed checkpoint. Release failure retains the blocked session; it must never silently permit a new engine. Victory/defeat can close using validated snapshots, with no rewards/penalties/growth. Terminal cleanup failure must not expose a successful settlement. Exact field layout and release-before-commit ordering will be fixed in the A contract before code.

No separate validated-but-uncommitted retry API planned; if one becomes necessary, it must guard the same revision/runtime generation and reuse the confirmation, never re-execute the engine. Remain synchronous; no remote/async protocol platform.

A acceptance: move finite/no-resource checkpoints, eligible switching, correlation/revision/identity/numeric rejection, one-in-flight/reentrancy, exact replay versus conflicts/old/future IDs, engine-advanced fault, abandon and cleanup-failure blocking, no partial state, two controlled adapters. Actual public vertical-slice code and tests reviewed; not an interface-only completion claim.

Gate A: stop REVIEWING and submit exact code/tests/evidence before implementing dependent B. An A PASS is not full F6 PASS and does not authorize F7.

## F6-B — medicine, fleeing and in-battle capture

Build only on reviewed A. Add one core-owned action contract for medicine (single stock debit), wild flee fail/continue and success/end, and capture fail/consume/continue versus success/consume/admit/record acquired. Trainer capture/flee forbidden before dispatch; trainer switching/medicine allowed. Minimal original capture item/config only; no arbitrary effect DSL or equipment.

Preflight total ownership capacity before irreversible capture dispatch. Full party routes successful capture to storage. Successful target uses its final validated HP/persistent state/resources and unique identity; captured is distinct from victory. Original controllable capture/flee inputs do not claim authentic Pokemon formulas. Define explicit adapter acknowledgement/effect/checkpoint ordering before code; do not let adapter and core both debit the same item.

Previously accepted failed-capture cost and checkpoint survive a later invalid confirmation. Faulted abandon gives no current capture/reward and no second current debit. Accepted exact receipt replay cannot duplicate stock effects or admission. No global receipt history or exactly-once claim across old snapshot rollback.

B acceptance: usable failed-then-successful capture sequence; finite/no-resource variants; trainer restrictions with switch/medicine success; empty/full/overflow capacity; illegal target/stock/result; exact duplicate/conflict/out-of-order behavior; engine advancement followed by invalid capture; abandon preserves prior costs; release failure cannot claim capture success. Retain all A and F1–F5 regressions. Two adapters and no-UI example use the same contract.
