# 怪兽 RPG 功能验收与审查

## 使用输入
读取当前功能任务卡、获准玩法覆盖矩阵对应行、上游已冻结契约、最终差异和实际测试记录。不要接受实现者一句“已测过”作为证据，不需要全量加载所有历史材料。

## 审查步骤
1. 核对本功能可观察价值及范围。边界类型齐全不等于玩家行为可完成；测试适配器通过不等于真实战斗系统已集成。
2. 运行项目已记录的类型检查、构建、相关测试。明确哪条命令没运行、失败或被环境阻塞。类型检查、声明产物、JS构建和运行测试各自负责不同问题，不能互相替代。
3. 通过公共API覆盖正常路径、非法输入、临界值、失败保持状态和必要重复/异步路径。输入来自unknown时检查运行时验证；禁止用any、断言或忽略诊断掩盖缺口。
4. 查看测试预期是否独立：原创规则手算或明确的不变量，不把待测函数输出直接当golden。
5. 依赖检查覆盖普通import、import type、re-export及实际使用的动态导入。核心不能间接带入引擎/DOM/fs；Vite仅是开发依赖，不能污染运行时契约。
6. 用具体文件位置、影响和复现方式报告阻塞项。缺陷修复后重新执行受影响验证，对最终文件集合给出结论。

## 审查结论
只用PASS / CHANGES_REQUIRED / BLOCKED，附版本或文件哈希、实际命令和输出摘要。自查与独立上下文Review必须分开标记。上游公共接口变化后重查受影响下游；不能沿用过期PASS。

## 最少反例
- 捕捉同一结果两次不能获得两只个体或扣两次道具
- 队伍满不是丢弃捕获个体的理由
- 错误技能引用和越界PP必须拒绝，不能仅靠TS类型
- 保存重载后治疗、成长、道具和图鉴记录要保持已承诺状态
- 第二套原创规则改容量/成长，第二个测试适配器改结果来源，核心源码不必跟着分支修改

来源与边界：用户项目规范第10至12、17节；实现资料包08。Node测试工具见 https://nodejs.org/api/test.html 和 https://nodejs.org/api/assert.html 。工具文档证明能力，不证明本项目测试已经执行。不要因审查启动新的外部写入、发布或突破项目预算。

补充反例：待学习与进化选择保存后恢复，choiceId/目标/候选/顺序不丢失，重复解决不再发奖；恢复前异步回调不改变新状态。引擎推进后返回非法捕捉确认，前一次合法失败消耗保留，当前动作不半更新，faulted会话可显式放弃恢复游戏，不无限卡死。战内换人不得重建或重置个体HP/资源。
