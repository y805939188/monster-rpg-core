# 怪兽 RPG 状态与战斗边界

先读取已批准验收矩阵中本行为的行及现有类型，不把任何旧方案中的简化当成已批准范围。

## 操作步骤
1. 列清每个字段的权威来源：物种/招式是内容定义；owned 中的个体、队伍引用、背包是长期状态；进行中战斗的临时 HP/PP/状态由战斗会话负责。禁止两份状态同时接受独立修改。
2. 对一个公开操作写出：输入校验、计算、提交、失败、重复、取消和恢复语义。规则计算失败时原输入保持不变。核心只接收复制且校验过的数据，不泄漏可变对象引用。
3. 跨适配器操作明确请求编号、关联会话、确认边界和迟到结果。不能因为调用Promise成功就提交未经校验的奖励，也不能把外部引擎已推进时的失败说成“全部回滚”。无法一致恢复时显式阻塞，等待既定恢复策略。
4. 重放先检查已处理回执，再要求pending或revision。相同已接受结果无额外效果；同ID不同内容拒绝；未知/未来ID拒绝。编号安全整数溢出前拒绝。取消已发编号不能复用。
5. 存档恢复先验证全体不变量，再替换运行状态。恢复/新游戏后让旧异步回调失效。声明去重仅对当前恢复分支有效；不能承诺跨进程或回滚旧存档的全局exactly-once。

## 捕捉示例
参考宝可梦基本玩法时，捕捉失败必须允许战斗继续，捕捉成功需要与战斗方的目标移除/结束确认对应；不能直接改成战后战利品而声称功能覆盖。球类道具只是具体规则内容。消耗道具、获得个体、队伍满留在持有集合、收集记录必须有明确一次提交边界。测试必须包含失败重试和重复确认，不只测成功捕获。

## 存档检查
校验物种/技能引用、ID唯一、队伍为持有集合子集且无重复、容量、HP/PP范围、经验与等级关系、道具计数、状态标识、回执/计数器关系以及内容/规则/存档版本。拒绝NaN、Infinity、不安全整数和未知版本。是否允许战中保存以获准矩阵为准；不支持就明确拒绝，不丢掉战斗状态后声称恢复完整。

## Review 检查项
- 适配器是可信战果生产者；输入校验不是反作弊或战果真实性证明
- 内存原子转换不等于磁盘事务；实际持久化归宿主
- 首个捕捉/成长/奖励失败是否真的保持核心原状态，而非测试替身替掉核心
- 新战斗取消后，旧成功回执编号可以小于最后发出的编号
- 去重记录保存边界与运行时代次不能混为一谈

来源与边界：用户项目执行规范第5、6、12节；实现侧资料包04/08；本项目独立设计Review。所有条款须结合当前获准玩法范围应用，不要求数据库、全局事件总线、分布式事务或事件溯源。

## 本期具体故障与选择策略
从获准基线读取故障策略：确认非法后faulted，停止新行动，不自动重执行引擎；显式放弃会话返回最近已提交核心检查点，保留此前已消耗道具，不给本次非法动作奖励。只对仍匹配revision/代次的合法未提交数据允许再提交。拒绝旧已消耗命令；无需无限结果日志。
待学习/进化选择需验证choiceId、目标、候选、顺序、未解决状态；保存恢复保留这些字段，解决选择只发生一次。恢复前回调必须在新运行代次拒绝。HP/资源在各结束结果与成长进化后的协调规则必须明确，不能任由适配器或调用顺序决定。
